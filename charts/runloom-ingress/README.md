# Optional ingress for Runloom

Updated: 2026-10-15. Audience: operators. The controller is a separate Helm release from the application. Both controller installation and application Ingress creation default to disabled. This chart wraps F5 NGINX Ingress Controller with NGINX Open Source, not the retired Kubernetes community `ingress-nginx` project. Upstream chart 2.8.0/controller 5.7.0 is pinned in `Chart.lock` and the included dependency archive. Normal application builds and upgrades do not fetch or deploy it.

## Choose ownership

| Mode | Controller release | Application values |
| --- | --- | --- |
| Optional NGINX | Install this chart with `nginx.enabled=true` | `values-ingress-local.yaml` |
| Existing controller | Do not install this chart | `values-ingress-external.yaml`; set your class and annotations |
| External Ingress, Gateway/HTTPRoute or load balancer | Do not install this chart | `values-routing-external.yaml`; platform routes to `<fullname>-ui:80` |
| Port-forwarding | Do not install this chart | Default application values; `ingress.enabled=false` |

The overlays live in [the application chart](../runloom). They do not configure databases, secrets, identity-provider clients or container images. Merge them with the complete installation values for your environment. `auth.publicURL` is independent of ingress ownership. The chart rejects mismatched Ingress/public hostnames and inconsistent TLS settings. Any controller supporting standard Kubernetes Ingress may be used; its class and annotation syntax remain operator-supplied. Gateway API resources are externally managed, not generated by Runloom.

## Optional controller installation

Check the explicit Kubernetes context before running these commands. The example targets local Kind, but creating a controller still creates cluster-scoped RBAC and an IngressClass. Never adopt or overwrite another controller release/class.

```sh
helm upgrade --install runloom-ingress charts/runloom-ingress \
  --kube-context kind-runloom-local \
  --namespace runloom-ingress --create-namespace \
  --set nginx.enabled=true --skip-crds --wait --timeout 5m
```

Use `--skip-crds`: this configuration uses standard Ingress only, with custom resources and snippets disabled. Upstream packages optional CRDs, but they are not needed here. The controller uses the non-default class `runloom-nginx`, a LoadBalancer Service and no NGINX Plus license. Vendor telemetry reporting is disabled. Further upstream settings can be supplied under `nginx.controller`, including Service annotations, resources and scheduling. Check upstream's supported Kubernetes versions before hosting this controller; successful template rendering alone does not establish runtime compatibility.

For an existing controller, skip this entire installation step. Do not install an empty controller release merely to select external mode. Disabling `nginx.enabled` on an already-installed controller release removes that release's controller resources; migrate all dependent routes first. Changing Runloom's application `ingress.enabled` never changes controller ownership. It does remove Runloom's own Ingress when disabled. Externally owned routes/controllers remain untouched.

## Hostname, HTTPS and identity

The supplied local overlays use `https://studio.runloom.dev`. This is a local alias proposal, not a claim of domain ownership. Public use requires ownership/control of the domain. For local use, explicitly map this hostname to the controller's reachable address and install a trusted development certificate for it. Do not rely on public DNS for a domain you do not own. The `.dev` suffix is HTTPS-only in browsers; plain HTTP or bypassing certificate verification is not a suitable setup. See [Google Registry's .dev guidance](https://www.registry.google/domains/dev/).

1. Provide host access to the controller. Docker Desktop Kind needs a host-access solution, such as [cloud-provider-kind](https://kind.sigs.k8s.io/docs/user/loadbalancer/), running separately. A LoadBalancer Service alone does not configure your Mac's DNS or hosts file. Do not recreate the cluster or delete PVCs to add ingress.
2. Provision a certificate trusted by your local browser. Create `runloom-local-tls` in the **application namespace**, using private certificate/key file paths. No certificate, private key or local CA is generated or trusted by these charts.
3. Set the public URL to `https://studio.runloom.dev` and align Keycloak client redirect URIs, web origins and post-logout redirect URIs. For bundled identity this also changes the issuer and Keycloak hostname; existing users will need to log in again. Realm import does not update an already-existing realm. Coordinate the existing client update before switching URLs; do not delete the identity database or recreate users.
4. Apply the application overlay together with your complete existing values. Keep database/token/vault Secret references and image versions unchanged. The local example below assumes those values have already been prepared privately.

```sh
kubectl --context kind-runloom-local -n runloom create secret tls runloom-local-tls \
  --cert=/private/path/studio.runloom.dev.pem \
  --key=/private/path/studio.runloom.dev-key.pem

helm upgrade runloom charts/runloom --kube-context kind-runloom-local -n runloom \
  --reset-values -f /private/path/current-runloom-values.yaml \
  -f charts/runloom/values-ingress-local.yaml --wait --timeout 10m
```

The Secret command creates a new Secret and refuses an existing name; use your established certificate rotation process for an existing Secret. For an existing controller, substitute `values-ingress-external.yaml` and set `ingress.className` to that controller's class. For platform-managed routing, substitute `values-routing-external.yaml`; the platform owns TLS termination and routes the same public origin to the UI Service. Keep service-owner APIs, databases, worker health and Prometheus private.

The UI proxy forwards the canonical host, protocol and port from `auth.publicURL`; it does not trust caller-provided forwarded host/protocol/port headers. This preserves the external HTTPS origin across the internal HTTP hop, regardless of controller vendor. The configured URL must match the real browser origin. Platform operators must restrict direct service access and configure their edge proxy securely.

Existing `make k8s-up`, `k8s-upgrade`, `k8s-open` and `k8s-run` helpers remain port-forward-only and intentionally reject hostname/ingress-based releases. Use explicit Helm commands for ingress deployments; these chart changes do not automate host networking, identity URL migration or certificate trust. The currently running local installation is not switched automatically.

## Checks and maintenance

```sh
make helm-lint
make helm-ingress-template
make helm-ingress-package
# Explicit dependency refresh from the lockfile, not required during app builds:
make helm-ingress-deps

kubectl --context kind-runloom-local -n runloom-ingress get pods,svc
kubectl --context kind-runloom-local -n runloom get ingress
curl --fail https://studio.runloom.dev/api/v1/health
```

After deployment verify browser login/logout, Angular remote loading, workflow start/status, and the external consumer endpoints. `helm test runloom` checks internal connectivity, not external DNS/TLS. No browser, DNS, certificate or live-controller rollout is performed by `make helm-lint`.
