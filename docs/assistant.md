# Lumi: assistant chat and authoring jobs

Source behavior updated 2026-11-09: private chat, durable planning jobs and automatic workflow draft saving in updated Studio. General chat can build new standalone main workflows. Workflow chat can fix or enhance the selected workflow draft, or create and attach a child draft. Publication, execution, schedule activation and credential-store access remain unavailable. Deployment must be verified separately.

## Using Studio

Select an organization and team, then open **Lumi** at the bottom center. The launcher expands into the chat dialog and the dialog contracts back on dismissal; reduced-motion preferences skip these transitions. Messages are private to your user within that team. Choose a conversation from history or use **New chat**. Enter sends; Shift+Enter inserts a newline. **Stop response** cancels the active planning job. A completed planning job means its response was generated, not that a workflow was created.

The assistant opens in a horizontally centered, Spotlight-style dialog whose bottom edge stays aligned with the launcher. It expands upward instead of moving to the center of the screen, with light/dark theme support and a responsive mobile layout. Use **⌘K** on macOS or **Ctrl+K** elsewhere to toggle it while Studio has keyboard focus. Escape, the close button or a click outside dismisses the dialog without cancelling a job or discarding the current draft. Keyboard focus stays inside while open and returns to the originating control when dismissed. Suggested prompts only fill the composer; sending remains explicit. Expand **Scope & guardrails** or **Drafts & queued messages** for details.

Inside workflow details, the assistant is scoped to that workflow definition (the main/parent canvas), not the selected node or run. Its header names the workflow. History, drafts, pending messages and planning jobs are isolated from general chat and other workflows. Selecting an inline node does not change scope. The saved root and reachable referenced children are included as full workflow definitions, including prompts, code, schemas, configuration, input mappings and structural outlines. This sends workflow content to the configured model provider and retains the authoring snapshot with the job; assess that provider and chat retention before using sensitive workflow content. Secret vault values and stored database connection records are not fetched. Opening another definition starts or restores that definition's separate scope; returning to the dashboard or Management restores general chat. Save a new draft before starting scoped chat; publishing is not required. Unsaved canvas changes are not supplied to the model.

The composer remains editable while a message is being submitted or a response is streaming. The dialog keeps the same dimensions when the first message is sent; message updates do not replay its opening animation. Pending and saved messages share a stable row keyed by the submission request ID, so acknowledgements update the existing bubble instead of replacing it. Newly sent messages ease into place over 600 ms without delaying submission. That animation does not repeat on acknowledgement or when reopening history, and reduced-motion preferences disable it. Space for response controls stays reserved to avoid shifting the composer during submission. Your submitted message appears immediately with a sending state; it is marked **Saved** only after the server confirms it. Typing the next draft does not alter the message already submitted, and acknowledgements never clear that new draft. Scrolling up to read earlier messages stops automatic following of streamed text.

While a response is active, Enter or **Queue message** saves another turn to the server-side queue. It runs in order even after you close the panel or leave Studio. **Stop and send** atomically stops the current response and puts the new turn next; other queued messages remain behind it. Partial text already saved remains visible. Cancellation is cooperative: the provider may take a short time to observe cancellation, and already-generated tokens may still be billable. The queued turns are processed serially, and future queued inputs are excluded from the prompt for the current response.

Drafts and messages not yet acknowledged are retained in this browser tab's session storage, keyed by signed-in user, organization, team, workflow scope and conversation. They survive refreshes, but this browser copy is not durable server storage: closing the tab or clearing browser data can remove unsent text. Signing out or changing accounts clears these local drafts when the app observes the identity change. No tokens or credentials are stored with drafts. If browser storage is unavailable, a warning advises keeping the tab open until acknowledgement.

For uncertain delivery, **Retry delivery** reuses the original request ID; automatic transient-error retries are bounded. **Dismiss local copy** removes only the local pending copy, never a message already accepted by the server. An SSE reconnect retrieves a persisted snapshot and reconciles request IDs, preventing duplicate messages or lost saved text. A failed stream does not cancel server jobs. History selection is temporarily blocked while delivery is unresolved; the message composer remains editable.

Chats allow 40 submissions and 120,000 bytes of message content; the live queue allows 10 waiting responses. HTTP 409 errors distinguish `conversation_limit`, `conversation_size_limit` and `queue_limit`. A full chat shows its limit beside **Move unsent messages to new chat** (or **Continue in new chat** if nothing is pending), rather than leaving messages labeled as waiting. A delivery failure labels later messages as blocked. **New chat** also moves pending messages once any in-flight request finishes. Before moving, Studio checks the old conversation for acknowledgements, then preserves only unsent messages in order with their request IDs and the editable draft, within the same user/team/workflow scope. It saves the new browser copy before removing the old local copy and starts delivery in the new chat. Failed reconciliation or browser storage leaves recovery stopped with the original unsent copy available. Saved history is never deleted; **New chat** clears the current message view, not the old conversation. Refresh the same tab to restore unsent messages after an upgrade; do not clear browser storage.

Messages and job status are stored server-side. Closing the panel or navigating away does not cancel the job. Reloading and reopening the panel restores the selected conversation. Failed responses retain persisted partial text and show a job error; sending a new message is an explicit retry that may incur model charges.

The model receives conversation text and, in workflow scope, authorized saved workflow definitions. It does not receive your access token, secret vault values, stored connection credentials or database rows. A literal credential or sensitive value already embedded in a workflow would be part of its definition: remove such literals and use configured secret/connection references before using Lumi. Do not paste credentials or sensitive customer data into chat. Text is rendered as text, not executable HTML.

## Building and saving workflows with Lumi

1. Configure a tool-capable provider. In general chat, ask Lumi to build a workflow with the required inputs and behavior. New Studio submissions enable automatic draft saving. When a valid definition is ready, Studio saves it in the team's default project and displays **Draft saved**. General chat cannot edit an unrelated workflow by an ID typed into chat.
2. To fix or enhance an existing workflow, open that saved workflow and Lumi, then describe the change. Valid pending canvas edits are saved before Lumi reads context. Invalid JSON or node-editor text remains local and blocks the request until corrected. Lumi uses the saved definition and authorized referenced children; only the selected workflow is updated. Open a referenced child separately to edit it.
3. The generated definition is saved using your current editor/admin access, editing locks and graph revision. An active lease owned by this canvas is reused for its root write; it is never reused for child drafts. Other tabs or users holding a root/child lock still block the write, and the error identifies the locked workflow. An expired lease requires recovery through the normal editor flow. A conflict or denied access prevents the write and shows an error. Resolve the conflict and request the change again when the saved context has changed. A transient save failure can be retried using **Retry saving draft**; duplicate requests reuse the same receipt.
4. Lumi saves drafts only. Publishing, running and activating schedules remain separate actions. **Workflow contract (JSON)** shows the generated definition; **View workflow before changes** shows the saved context used for an update. Validate the business behavior before publishing.
5. Child creation/attachment still uses empty child input. Complete its input mapping manually, or ask Lumi to update the root's Subworkflow `with` mapping. Publish and pin the child explicitly before executing the parent.
6. Automatic saving runs in the authenticated Studio client while its conversation receives updates, and resumes when that conversation is reopened. Closing Studio before the result arrives leaves the generated result pending until reopening; the backend does not retain your bearer token. Older jobs without automatic-saving authorization still require **Apply draft changes**. Previously queued browser messages retain their original saving mode when restored.
7. Lumi returns the complete workflow contract through its structured workflow tool; Studio displays **Workflow contract (JSON)** and the confirmed draft-save status. The API retains historical `proposal` field names for compatibility; these do not add a review step to automatic draft saving. New workflows and structural edits (inserting, deleting, reordering or changing paths) use Studio’s complete automatic graph arrangement rather than model-generated coordinates. Settings-only edits preserve valid saved canvas positions; omitted or invalid layout on those edits falls back to the authorized saved layout. Execution fields are never discarded or repaired by this layout normalization. The Assistant checks generated definitions against its embedded workflow schema. The owner validates configuration and graph restrictions again before saving. Invalid or truncated definitions are never partly applied. These checks do not prove business correctness or connection availability. Supply required model names, secret names and connection IDs; Lumi must not invent them.
8. Context is limited to 64 KiB, generated workflow JSON to 48,000 bytes and 100 top-level nodes. Nested limits follow the workflow contract. Configured output tokens default to 2048, maximum 8192. Model calls can incur cost even when generation or saving fails.
9. The builder refreshes confirmed updates only when it has no unsaved changes. If this canvas owned the editing lease, Studio reloads the saved result and attempts to resume editing; a newly acquired competing lease is respected. General-chat creation refreshes the workflow list when available; open the new draft from that list. Undo history does not cross a server reload; use commit History to restore a saved draft.

## Upgrade and verification

Upgrade Workflows API first, then Assistant, then the Studio applications together with matching platform package versions. Platform 1.8.0 adds scalar-only draft coordination methods; all four applications must use the same packaged platform version because runtime sharing enforces exact compatibility. The workflow app keeps its lease private, forwards it only on an authenticated scoped save, and the Assistant does not persist it or send it to the model. The Assistant embeds its own workflow-schema snapshot for independent builds; after contract changes run `make sync-assistant-contract`, refresh dependencies with `make vendor-go`, and verify `make check-assistant-contract`. Existing child-attachment requests remain accepted. Full-definition context is explicitly requested by the new Assistant with `X-Runloom-Authoring-Context: full`; older callers continue receiving structural outlines by default. Updated Studio requests `authoring_version=2`; older clients retain child-only authoring and do not receive proposals they cannot review. No data migration or credential rotation is introduced by these new operations; the existing authoring receipt storage is reused.

Source verification on 2026-11-09 includes schema/tool stream tests and disposable PostgreSQL/MongoDB transaction tests. Model responses in those tests are synthetic; they do not prove a real model will generate correct business logic. Automatic-saving controller and browser tests also use mocked model/API responses. Separately, on 2026-11-09, the local Kind installation was verified with live `gemini-3.5-flash-lite`: Studio automatically created a synthetic Wait → End draft, read it back with `version=0`, then generated and saved a scoped edit changing the wait from one second to two seconds. The saved edit was read back through the API. No workflow was published or executed. The follow-up lease fix was also verified live on that date: Lumi saved an edit while the canvas retained its own editing lease, then reloaded and resumed editing. A second check made a pending canvas name edit immediately before sending a Lumi request; the name was preserved and the generated wait change was saved and read back. Root/child lock rejection, wrong-owner and stale-token handling, invalid JSON, save waiting, navigation interruption and non-fallback after a denied save have regression coverage. The reservation tests stub transaction entry and do not establish database durability; the prior PostgreSQL/MongoDB tests cover persistence separately. This verification used the working tree based on `09e0aa1`; it is not evidence of a production deployment.

Live verification on 2026-11-10 reproduced a callback-edit failure caused by an invalid `@@trigger` canvas key. After layout normalization, the same chat request generated a valid workflow contract, Studio displayed **Workflow contract (JSON)**, and the callback draft was saved and read back through the API. No workflow was published or run. Regression tests also verify that invalid execution nodes remain rejected and valid generated layouts are preserved.

Canvas verification on 2026-11-10 confirmed that the latest generated workflow rendered without overlapping cards while its existing editing lease remained untouched. A disposable nine-node nested-branch scene was auto-arranged, all displayed positions were saved and read back, and its execution fields were unchanged. The disposable draft was removed. ## Configuration

Configuration is a startup snapshot. Restart the assistant after changes. With an absent or disabled provider, chat remains enabled: each user message is saved together with the assistant reply “LLM is not configured.” This is a configuration notice, not a model-generated answer. Its job is completed immediately with an empty model and no model call or charge. Both messages remain available after reloading, and users can continue chatting. These notices are excluded from model context if a provider is enabled later. Invalid configuration for an explicitly enabled provider still fails startup validation.

For Compose, edit [compose/config/assistant.yaml](../compose/config/assistant.yaml):

```yaml
RUNLOOM_ASSISTANT_PROVIDER: openai-compatible
RUNLOOM_ASSISTANT_BASE_URL: https://your-provider.example/v1
RUNLOOM_ASSISTANT_MODEL: your-model
RUNLOOM_ASSISTANT_API_KEY_FILE: /run/secrets/assistant-api-key
RUNLOOM_ASSISTANT_ALLOW_HTTP: "false"
RUNLOOM_ASSISTANT_MAX_TOKENS: "2048"
```

The endpoint must implement streaming Chat Completions, including `max_completion_tokens`, text deltas, finish reasons and the `[DONE]` marker. Workflow proposals additionally require streamed function calls, schema-conforming arguments and `parallel_tool_calls: false`; unsupported providers fail closed without writing. The standard compatibility path requests strict tool schemas; Gemini uses the structured schema adaptation described below and the same server-side validation. Tool argument fragments follow the [official function-calling stream contract](https://developers.openai.com/api/docs/guides/function-calling). Provider compatibility must be tested with the selected model. This adapter follows the [official streaming-event contract](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events). It does not support every vendor's native API.

For Gemini, use `https://generativelanguage.googleapis.com/v1beta/openai` as the base URL and select a model available to the credential. The adapter omits `store` for that Google endpoint because it rejects the field; provider retention and training terms still apply. Gemini workflow authoring uses structured object tool arguments and accepts its `stop` finish reason for an otherwise valid tool call. The generation schema relaxes recursive array minimums for Gemini compatibility; the unchanged authoritative schema still validates the result before saving. A schema-invalid workflow gets at most one correction attempt, within the same five-minute deadline. This can make a second model call and consume additional quota or cost. Authentication, quota, overload and network failures are not retried automatically. Verify streaming and workflow proposals with the selected model before relying on it.

Set `RUNLOOM_ASSISTANT_API_KEY_PATH` to an existing local credential file before `make local-services-up SERVICES_DATABASE=mongodb` or `SERVICES_DATABASE=postgres`. The key is mounted as a secret, not put in YAML or sent to the browser. For a trusted local unauthenticated provider, the key file may be empty and `RUNLOOM_ASSISTANT_ALLOW_HTTP` must explicitly be `"true"`. Provider URLs are operator-controlled; users cannot change them through chat. HTTP redirects are rejected.

For Helm, configure:

```yaml
assistant:
  enabled: true
  provider: openai-compatible
  baseURL: https://your-provider.example/v1
  model: your-model
  maxTokens: 2048
  apiKeySecret: runloom-assistant-provider
  apiKeyKey: api-key
  databaseName: runloom_assistant
  databaseSecret: runloom-assistant-database
  databaseURLKey: url
```

The provider Secret can be provisioned by an external-secrets controller. Hosted operators must supply the owner database URL Secret. With `databaseSetup.enabled`, that Secret also needs the `password` key for the setup Job; the assistant itself mounts only the URL key. Local `make k8s-up` / `make k8s-upgrade` creates additive assistant database credentials without replacing existing service credentials or data. `assistant.enabled: false` omits its Deployment, Service and gateway route.

Compose provisions `runloom_assistant` with a separate owner on both databases. The setup Job verifies that service owners cannot access each other's databases. No shared application tables or cross-service database imports are used.

## Security and lifecycle

Workflow chat adds an immutable `workflow_id` query parameter on every assistant route. The API verifies the caller's access to that saved definition (draft or published version) through the workflow owner's Studio API using the same human bearer and authorized team. Missing/deleted/inaccessible workflows fail closed, including SSE reconnects; a workflow-service outage returns 503 rather than general-chat fallback. The active SSE connection renews these checks within 15 seconds. Other workflow IDs or omission of the stored ID cannot read, append to, cancel jobs in, or replay creation of that conversation. Scope never changes through chat text. The model receives the embedded [guardrail prompt](../server/assistant/internal/chat/guardrails.txt), authorized saved workflow context, the bundled node schema and proposal-only tools. Prompt instructions are guidance, not authorization. Actual isolation and writes are enforced by the APIs and owner database.

`RUNLOOM_WORKFLOWS_URL` is the operator-controlled workflow-owner base URL. Compose and Helm supply it automatically. Native installations must supply it for workflow-scoped chat; discussion remains available without it, but draft creation requires the workflow-owner authoring API. No privileged service token or workflow database credentials are added. Startup adds a PostgreSQL workflow-scope column/index or a MongoDB compound index. Existing records without a workflow scope remain general chats; they are not reassigned or deleted. Complete the backend rollout before enabling the new UI; do not run old assistant replicas or roll back to a scope-unaware backend once scoped conversations exist. The platform library release 1.6.0 adds optional details-context metadata and a safe post-apply refresh callback; all three federated apps must use matching compiled package versions.

The assistant verifies signed human Studio tokens using the independently vendored Go token SDK, then checks live team membership through Auth's public `/api/v1/studio/me` endpoint. Service-account tokens and forged identity headers are not accepted. Conversations require the original user, organization, team and optional workflow scope on every read/write, including stream reconnection. Tokens are never persisted. A job authorized when submitted may finish planning after the browser closes; it has no execution tools or persisted delegated credentials. A saved-definition snapshot is obtained with the current human bearer at submission; applying rechecks live permissions and the complete graph revision with a new authenticated request.

Model-backed authoring jobs transition from `queued` to `running`, then `completed`, `failed`, `cancelled` or `interrupted`. Without a provider, the configuration notice and its already-completed job are saved directly with the user message. Jobs are `kind: planning` in general chat or `kind: authoring` with saved workflow context. A completed job may contain an immutable proposal and review hash; completion alone never writes a workflow.

Message and job insertion, queue ordering and stop-and-send cancellation are atomic through a bounded conversation aggregate. PostgreSQL uses a revision-checked row update; MongoDB uses a revision-checked single-document replacement, so standalone MongoDB is supported. A worker claims the next active job through that revision check. Other replicas cannot claim it twice. Streamed progress merges only that running job and its response into the latest revision, preserving concurrent queue submissions. A cancelled or expired job cannot overwrite newer state. A lost running job is marked interrupted after its two-minute lease, rather than automatically generating another billable request; the next queued turn can then proceed.

The API sends persisted snapshot events, not an ephemeral in-memory event log. Clients replace snapshots by revision rather than appending duplicate tokens. Streams reconnect every 15 seconds with renewed authentication. There is a bounded revocation window for an already-open stream; a new connection checks current membership.

The model instructions favor concise replies and direct proposals when sufficient context is available; these instructions do not guarantee provider latency.

While a job is queued or running, Lumi displays a progress indicator beneath its response, including while a workflow proposal is being prepared. This is an activity indicator, not measured node-building progress. Reduced-motion preferences disable the animation. Failures appear directly with the response; a worker deadline explains the five-minute limit and preserves partial text.

Limits: 8,000 UTF-8 bytes per user message, 40 turns per conversation, up to 10 waiting turns plus the replacement turn during stop-and-send, approximately 120 KB stored context before accepting another turn, 32 KB generated response, five-minute provider timeout, a worker recovery deadline ten seconds beyond the response limit, four worker slots per replica, and configured output tokens between 1 and 8,192. Each conversation has one logically running job plus queued turns. No automatic retry of provider failures is performed; Gemini workflow-schema correction is limited to one additional generation. Public exposure additionally requires ingress-level rate limits and appropriate provider quotas; this release does not enforce monthly authoring spend budgets or add these costs to workflow-run analytics.

Chat history persists until operator-managed deletion; automatic retention, user export/deletion, attachments, sharing and full compliance workflows are not included. Operators must configure database encryption/backups and an appropriate retention policy before using sensitive data.

## API and verification

The [OpenAPI document](../server/assistant/api/openapi.yaml) describes versioned Studio endpoints. All conversation routes require `org_id` and `team_id`, plus the same `workflow_id` for workflow-scoped chats. List pagination uses an ID cursor, not chronological ordering. Message submission requires a UUID `request_id`; retry the same ID, text and mode after uncertain network failure. Reusing it with different text or mode is rejected. The optional `mode` is `send` (default, rejects active work), `queue` or `stop_and_send`. Once accepted, retrieve the conversation to find the job ID and its original request ID. Queue-aware server and worker code must be deployed before exposing the new UI; do not roll back to a worker that assumes only the last job can be active while queues remain.

```sh
make test-assistant
make test-assistant-live
node scripts/test-authoring.mjs
make build-assistant
cd studio/projects/host && npm test && npm run build
```

For the browser smoke, an existing local Studio/Keycloak must be reachable. Build the host and assistant, supply an installed Playwright module with `RUNLOOM_PLAYWRIGHT_MODULE` and optional Chrome executable via `RUNLOOM_CHROME`, then run `node scripts/test-assistant-browser.mjs` from the repository root. It uses real local login and disposable assistant databases with a synthetic streaming provider; it does not create workflows or alter the existing application database. Repeat with `RUNLOOM_ASSISTANT_TEST_DISABLED=1` to verify sending, saved configuration replies, reload persistence and subsequent messages without a model on both databases. Local public test credentials are defaults; override `RUNLOOM_TEST_EMAIL` and `RUNLOOM_TEST_PASSWORD` privately if needed. This is not verification of a paid model provider.

Opt in with `RUNLOOM_ASSISTANT_TEST_AUTHORING=1` to also create isolated `assistant-smoke-*` parent drafts and child drafts in the selected local team. This checks proposal review, edit-lock UI guards, parent attachment, draft-only state and receipt reload through real Studio authentication and the workflow owner. Those named smoke drafts remain available for inspection; existing workflows are not modified. Do not run database matrices concurrently with Docker builds on a memory-constrained local cluster.

Lumi can create and edit independent [Temporal signal handler paths](signal-handlers.md) using `signal_handlers` in the workflow contract. These receive events in an existing running execution; the main path must remain open for future events.

Generated complete workflows use the authoritative workflow schema limit of 500 nodes; Lumi does not impose a separate 100-node limit on the main path. A missing name, malformed definition or changed selected workflow ID enters the same single correction attempt as invalid node fields. An update never rewrites the selected ID silently or saves a contract that still fails validation. If correction fails, preflight errors identify the failed condition and leave the draft unchanged.

## Revert a saved Lumi edit

After Lumi saves an update to an existing workflow, select **Revert Lumi change** beneath that response to restore the draft from before that edit. Restoration creates a new draft history entry and records an audit event; it does not publish, start a run, remove history or reverse external effects. It restores the complete root definition, including signal handlers and layout, without calling the model. Unsaved editor changes must be resolved first, and normal team permissions and editing reservations apply.

A fingerprint check blocks restoration if the saved draft changed after that Lumi edit. Use workflow draft history to select a revision when you intentionally want to replace newer changes. Repeated successful clicks do not create duplicate restore commits. The response retains **Previous draft restored** after reopening the chat. Creation and child-attachment messages do not offer this action; reverting an update does not delete child workflows. Older update receipts can match their original generated definition, but chats without a full pre-edit definition must use draft history. Missing child dependencies or lost permissions can prevent restoration.

Verification on 2026-11-10: Go workflow/Assistant tests, Host/Workflows UI tests and production builds, OpenAPI generation checks and documentation synchronization passed. A browser test with synthetic chat generation used the real local owner API, edit lease and application database to restore the exact prior draft, including signal handlers, and confirmed that an identical restore retry created no extra history entry. A real-provider end-to-end generation attempt was blocked twice by provider overload before any model edit was saved; it does not verify successful live model generation.

## Workflow development requests

Studio asks Lumi for a workflow action on each draft request. A completed generation returns a workflow contract for Studio to save or asks a specific question about a missing requirement. For example, a database write needs a destination connection and table or collection. A saved-draft receipt confirms that the workflow service committed the change.

Lumi retries a transient provider outage, interrupted response or text-only generation once within the same five-minute job deadline. A provider-specified retry interval leaves the retry to the caller. Validation can request one corrected complete contract. The recursive workflow schema still governs saves. The Gemini generation tool uses a smaller schema with the supported node types, and validation reports the affected step when it can identify one. Provider availability, generation limits, validation errors and save conflicts can still prevent a requested edit.

Verified on 2026-11-10 in the local Studio deployment with Gemini. Four consecutive requests created a timer workflow, corrected its duration, inserted another timer, and removed the added timer. Each saved definition was read back before the next request.
